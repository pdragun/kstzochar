# AGENTS.md

Guidance for coding agents (Claude Code, Codex, Cursor, Copilot, Gemini CLI, …) working in this repository. Claude Code reads it through `CLAUDE.md` and Gemini CLI through `GEMINI.md`, which import it; Codex, Cursor, Copilot and most other agents read `AGENTS.md` directly. Keep project knowledge in this file, not in the agent-specific ones.

## Project

Symfony 8.1 (Doctrine ORM 3, DBAL 4; PHP >= 8.5) website for the Slovak hiking club "KST Žochár Topoľčany" (live: https://kst.zochar.sk). All user-facing content, URLs and route paths are in Slovak (e.g. `/pozvanky`, `/kronika`, `pridat-novu`).

## Local development

The local stack is Docker Compose (FrankenPHP + PHP 8.5, a database, project services), driven by [Task](https://taskfile.dev): `Taskfile.yaml` holds this project's tasks and includes `taskfiles/common.yaml`, the tasks shared by all these projects. `task --list` shows them all.

- **Always go through `task`** for anything that runs project code or touches the stack: Docker, PHP, Composer, `bin/console`, PHPUnit, php-cs-fixer, phpstan, rector, npm and Node. Never run `php`, `composer`, `bin/console`, `vendor/bin/*`, `npm`, `node` or `symfony` on the host: the host's PHP and Node differ from the containers' and don't see their environment. Don't call `docker compose exec` or `docker compose run` yourself either. If no task fits, use `task docker:exec COMMAND="…"` (php container) or `task node:exec COMMAND="…"` (node container), or add a task: shared ones to `taskfiles/common.yaml` (then copy that file to the other projects), project ones to `Taskfile.yaml`, personal ones to the git-ignored `Taskfile.local.yml`.
- Commands shown bare elsewhere in this file or in the project's docs mean their task form: `bin/console about` is `task console -- about`, `composer require foo/bar` is `task composer -- require foo/bar`, `bin/phpunit --filter testFoo` is `task test -- --filter testFoo`, `npm run build` is `task npm -- run build`.
- Reading and editing files, `git`, and `docker compose ps` / `logs` on the host are fine.
- If Docker or the php container is unavailable, report it and stop. Don't fall back to the host's PHP, Composer or Node.

```bash
task up                   # build and start the stack (task down stops it, task dr recreates it)
task ps / task logs [-- <service>]   # services, health and ports / follow the logs
task sh / task dbsh       # shell in the php container / database client as the app user
task console -- <args>    # bin/console (alias: task c)
task composer -- <args>   # composer; task install = composer install, cache clear/warmup, assets:install
task cc                   # clear and warm the dev cache (APP_ENV=test task cc for the test cache)
task test [-- <args>]     # prepare the test database, then phpunit, e.g. task test -- --filter testFoo
task check                # all of this project's checks (code style, static analysis, tests)
task cs / cs:check        # php-cs-fixer fix / dry run, where installed; also task stan, task rector
task dms / dmm / dmd      # migrations status / migrate / diff, where the project uses migrations
task dv [-- --env=test]   # doctrine:schema:validate
task db:grant-test        # grant the app user its <database>_test databases on an existing volume
task npm -- <args>        # npm in the node container; task build = production assets
task fix-perms            # hand root-owned files and Caddy volumes back to your user (no sudo)
```

- **File ownership.** The dev php image runs as a user `app` with your host user's ids (`USER_UID`/`USER_GID` build args in `compose.override.yaml`; Task passes yours, a bare `docker compose` assumes 1000:1000), and the node service runs as you too. Everything they write into the bind-mounted project (`var/`, `vendor/`, `node_modules/`, `public/build/`, generated code, migrations) stays yours. Don't use `-u root` for project commands. `task fix-perms` is only for files left by a stack that ran as root; after changing your ids, rebuild with `task up`.
- **Logs.** `var/` lives in the project directory, so read `var/log/dev.log` and `var/log/test.log` directly; `task logs -- php` shows FrankenPHP's output, and the web profiler is at `/_profiler`. Read them before changing code when something fails.
- **Startup.** The php container's entrypoint runs `composer install` only when `vendor/` is empty (run `task install` after a `composer.lock` change), waits for the database and runs pending migrations, if the project has any. With `--watch`, FrankenPHP restarts its PHP workers when files change.
- **Makers.** `task console -- make:… --no-interaction` with every argument passed up front: makers prompt by default, which hangs a non-interactive shell. If one still needs input, write the code by hand.
- **Configuration.** `.env` is committed and holds defaults only. Real secrets go in `.env.local` (git-ignored) or the secrets vault (`task console -- secrets:set`). Compose takes the host ports from the shell environment (`HTTP_PORT`, `HTTPS_PORT`, `HTTP3_PORT`, `DATABASE_PORT`); the defaults are below, project-unique so the stacks run side by side.

## Local environment

- Services: `php` (FrankenPHP in classic, non-worker mode, container `kstzochar-php`, workdir `/app`), `database` (MySQL 8.4, `kstzochar-database`), `node` (Webpack Encore: `npm install`, then `npm run watch` into `public/build/`, `kstzochar-node`; it waits for php, because Encore copies the CKEditor files from `vendor/`).
- URL: `https://localhost:18443/` (accept the self-signed certificate; plain HTTP `18080` on 127.0.0.1). Caddy listens on the published HTTPS port itself (`SERVER_NAME` carries it), so its HTTP->HTTPS redirect keeps the port.
- DB: `localhost:3311` from the host (127.0.0.1 only), `database:3306` from the containers; database `kstzochar` (+ `kstzochar_test`), user `app`, password `!ChangeMe!`. In Docker, `DATABASE_URL` comes from `compose.yaml` (real env vars win over `.env*` files).
- Fixtures (`src/DataFixtures`) provide the dev and test data, including the admin and member users the tests log in as (e.g. member `jana.novakova@example.com`).
- `task dbr` drops every table (including `doctrine_migration_versions`), migrates and loads fixtures (asks first; `APP_ENV=test task dbr` for the test database). Recreating the schema also resets auto-increment ids, which the tests depend on.
- Static analysis: `task stan` (phpstan level 6, `phpstan.neon`, with phpstan-doctrine and phpstan-symfony; needs the dev container in `var/cache/dev`), `task rector` / `task rector:check` (`rector.php`). `task check` = stan + rector:check + test.

### Tests and the test database

Tests run in `APP_ENV=test`; Doctrine appends `_test` to the database name (`config/packages/doctrine.yaml`), so they use `kstzochar_test`. The functional tests assert against fixture data and the suite mutates it, so `task test` first resets the test database (`task test:setup`, also `task ts` / `task tdbr`: drop, migrate, fixtures), then runs PHPUnit 13 (`symfony/phpunit-bridge` extension) with `memory_limit=1G`, e.g. `task test -- tests/Controller/BlogControllerTest.php` or `task test -- --filter testShowInvitation`. The MySQL init script `docker/mysql/init/10-test-database.sh` creates `kstzochar_test` and grants the `app` user the `kstzochar\_test%` databases, but only on a fresh data volume: on an older volume, `task db:grant-test` applies the grant once (data is kept).

### Migrations

The schema comes from Doctrine migrations (`migrations/`, namespace `DoctrineMigrations`); locally the php container's entrypoint runs `doctrine:migrations:migrate --all-or-nothing` on start. Schema changes go into a new migration (`task dmd`, then review it, then `task dmm`); keep migrations transactional (the default), because `--all-or-nothing` refuses non-transactional ones. Production runs on shared hosting without Docker (the Docker setup is for local development only), so migrations are run there by hand on deploy (README, "Production"). `Version20000101000000` is a baseline with the schema from before migrations existed: on a database that already has the tables (production, which was created with `doctrine:schema:create`) it runs no SQL and is only recorded as executed (not `skipIf()`, because skipped migrations aren't recorded).

## Architecture

- **Domain model**: `Event` (`src/Entity/Event.php`) is the parent "plan" entry for a date. It has optional one-to-one links to an `EventInvitation` (pozvánka, before the event), an `EventChronicle` (kronika, report after the event) and a `Blog`. Invitations and chronicles have many-to-many `SportType`s and `EventRoute`s. Creating an invitation or chronicle is a two-step flow: first pick a date (`SetDateType`), then `.../pridat-novu/{date}/add` looks up an `Event` on that date and pre-fills title, dates and sport types from it; a new chronicle also starts with the routes of the event's invitation (`Event` has no routes of its own). Routes are shared entities: when saving, a route that also belongs to another invitation or chronicle and was edited is replaced by an edited copy (`SharedRoutes`), and the original keeps its data. An invitation has an optional start `Location` (meeting place: name, town and country, optional street, postal code, region and coordinates; names are unique, case- and accent-insensitive through the MySQL collation). The form offers a select of existing locations and an unmapped "new location" sub-form (`LocationType`) that wins over the select when filled; the detail page shows it as a microformats `p-location h-card`. Admins fix locations on `/miesta-stretnutia` (`LocationController`: list with invitation counts, edit with `LocationType`'s `standalone` option, merge a duplicate into another location, delete only when no invitation uses it, because the foreign key is `ON DELETE SET NULL`). Chronicles have no location. Structured data for search engines is JSON-LD built in `App\Twig\StructuredDataExtension` (breadcrumbs in `base.html.twig`, a schema.org `Event` in the `head` block of the invitation detail page); its `event_iso_date` filter reinterprets the stored wall-clock dates (PHP runs in UTC) in `Europe/Bratislava` and gives only the date for 00:00. The invitation detail page also carries a microformats `h-event`. Blog posts and chronicles (both implement `App\Entity\Article`) get a `BlogPosting`/`Article` JSON-LD, an `h-entry` and a visible byline (`templates/_article_byline.html.twig`); the author is `authorBy ?? createdBy` (`article_author()`, shown by `displayName`, `authorBy` is a select in the blog and chronicle forms), the date `publishedAt ?? createdAt`. Those timestamps are real UTC instants, so they go through `iso_timestamp` (converted to Bratislava time), not `event_iso_date`.
- **Event dates and the calendar export**: `startDate`/`endDate` of events, invitations and chronicles are stored as the local Europe/Bratislava wall-clock time the admin typed, not as UTC. That is deliberate (the year in URLs comes from `SUBSTRING(startDate, 1, 4)`), so don't convert them on save. 00:00 means that no time was set. Only real instants (`createdAt`, `publishedAt`, `modifiedAt`) are UTC. `App\Service\EventTime` holds the conversions. `InvitationCalendarController` serves an invitation as iCalendar (`/pozvanky/{year}/{slug}/kalendar.ics`) and a feed to subscribe to (`/pozvanky/kalendar.ics`, published invitations from 90 days back), both built by `App\Service\InvitationCalendar` (hand-written RFC 5545: escaping, 75-octet folding, times in UTC, an all-day event when there is no start time, a default end at 18:00 when there is no end date; the `UID` is `invitation-{id}@kst.zochar.sk`). Unpublished invitations are never exported.
- **Page head**: `base.html.twig` builds the `<title>`, meta description, canonical link and Open Graph tags from the child's `title` block (which ends in ` - `; `page_title` is it trimmed, and `og:title`), its `description` block (default `base.description`), `og_type` (`website`, `article` on blog and chronicle pages, which add `article:published_time` through `_article_og.html.twig`) and `canonical_url` (default: the current route and its parameters, so query strings drop out; detail pages override it with the entry's own URL, because slugs match case-insensitively). Google Analytics exists only when the `ga_measurement_id` Twig global (env `GA_MEASUREMENT_ID`, empty outside production) is set: then `base.html.twig` adds the consent banner (`_cookie_consent.html.twig`) and the `cookieConsent` Encore entry (outside the `javascripts` block, which pages override), which loads gtag only after the visitor accepts and keeps the choice in the `cookie_consent` cookie; declining deletes the `_ga` cookies. `/cookies` (`CookiesController`) lists the cookies; keep it in sync when adding any.
- **Controllers** (`src/Controller/`) use attribute routes. Content is addressed by `/{section}/{year}/{slug}`. Slugs are regenerated from the title on every create/edit by `App\Service\SlugGenerator`, which appends `-2`, `-3`, … when another entry in the same URL scope uses the slug (the start-date year for invitations and chronicles, section plus `createdAt` year for blogs; each repository has a `slugExists()` check that skips the entry itself). Write actions are guarded with `#[IsGranted('ROLE_ADMIN')]`. Edits of many-to-many collections follow the Symfony "embed a collection of forms" pattern: snapshot the original collections, then remove orphaned links before `flush()`. For invitations and chronicles (both implement `App\Entity\EventContent`) this lives in `App\Service\EventContentEditor`: the controller takes an `EventContentSnapshot::of($content)` before `handleRequest()`, then calls `create()`/`update()` (slug, timestamps, shared routes, orphaned links, flush, cache) or `delete()`, and keeps only the flash message and the redirect. `prefillFromEvent()` does the pre-filling described above. Blogs have the same split with `App\Service\BlogEditor` (no routes; the slug scope is section plus `createdAt` year). The front end uses `@a2lix/symfony-collection` (`assets/js/a2lixSfCollection.js`).
- **Caching**: the `content.cache` pool (`config/packages/cache.yaml`, `cache.adapter.doctrine_dbal` on the default Doctrine connection, so tests use the `_test` database) is autowired as `$contentCache`. It caches the `home-page` data (`HomePageController`, expires at midnight because it holds date-relative queries) `main-menu-data` (`src/Menu/Builder.php`, the KnpMenu main menu with years and items for every section) and `sitemap` (`App\Service\SitemapBuilder`, the route names, parameters and `lastmod` of every public page for `/sitemap.xml`; `SitemapController` also serves `/robots.txt`, which points to it). **Any action that creates, edits or deletes content must call `$contentCache->clear()`** (`EventContentEditor` and `BlogEditor` do it; other controllers take `CacheItemPoolInterface $contentCache`), otherwise the menu and home page show stale data.
- **Menu and breadcrumbs**: KnpMenuBundle builder registered as `app.menu_builder` in `config/services.yaml`, rendered through `templates/extended_knp_menu.html.twig`.
- **Translations**: UI strings are being moved into `translations/messages.sk.yaml` (Slovak only). Prefer adding keys there over hard-coding strings in controllers or templates.
- **GPX**: `App\Service\Gpx` wraps `sibyx/phpgpx` to sanitize uploaded GPX tracks (it resets metadata and author) before `GpxController` serves them. `/gpx/{id}` serves a route only when it belongs to a published invitation or chronicle (admins get every route), because routes stay in the database after they are removed from content.
- **HTML sanitizing and headers**: the CKEditor `content` of invitations, chronicles and blogs is cleaned by the `app.article_sanitizer` HTML sanitizer (`config/packages/html_sanitizer.yaml`: safe elements plus `style` and `class`, no iframes, no input length limit) twice: on save (the form fields' `sanitize_html` option) and on render (`|sanitize_html('app.article_sanitizer')` instead of `|raw`, which also covers older rows). Saving stores HTML entities as plain characters. `App\EventListener\SecurityHeadersListener` adds `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy` and a `frame-ancestors` CSP to every response (a listener, because production runs on Apache); in debug mode Symfony removes the CSP header from error pages.
- **Auth**: built-in `form_login` against `User` by email (`config/packages/security.yaml`, `LoginController`). `ROLE_ADMIN` inherits `ROLE_USER`. `login_throttling` refuses logins after 5 failed attempts in 15 minutes (counted in `cache.rate_limiter`, which `LoginFormTest` clears in `setUp()`); logout needs a CSRF token, so link to it with `logout_path()`, not `path('logout')`. `AdminAccessTest` lists every admin URL and checks that a member (`jana.novakova@example.com`) gets 403: add new write actions there.
- **Tests** (`tests/Controller/`) are functional `WebTestCase`s. Data providers are static methods wired with `#[DataProvider]` attributes; `phpunit.xml.dist` fails the run on deprecations, notices and warnings from `src/`. They check status codes (200, 404 via data providers, 302 redirects to login for admin routes) and assert Slovak text from the fixtures using CSS and XPath selectors.
- **Docker**: `Dockerfile` (stages `frankenphp_dev`, `frankenphp_prod`, `assets_builder`), `compose*.yaml`, `frankenphp/` (Caddyfile, php.ini, entrypoint). FrankenPHP runs in classic mode; worker mode has not been tested.
- **Frontend**: Encore entries `app`, `a2lixSfCollection`, `newLocation` (hides the invitation form's "new location" fieldset behind a button), `cookieConsent` (the cookie banner) and `css/app` (SCSS, Bootstrap 5). Encore also copies images, downloads and the CKEditor assets from `vendor/friendsofsymfony/ckeditor-bundle` into `public/build/`.
