# Fix plan for the 2026-10-05 review

**Status: done.** All phases merged on 2026-10-06 (PRs #9 to #17, details per item).

Source: [`code-review-2026-10-05.md`](../reviews/code-review-2026-10-05.md) (findings #1 to #10 plus the lower-priority notes).
The work is split into four phases. Each phase can ship as its own branch and pull request, and later phases do not depend on earlier ones unless a step says so.
Every step adds or updates a functional test in `tests/Controller/`. After each phase, run `bin/phpunit`, `vendor/bin/phpstan analyse` and `vendor/bin/rector process --dry-run` inside the php container.

## Phase 1: Crashes and security (small, low risk)

### 1.1 Login page 500 for logged-in users (finding #7)
Done in PR #9.
- `templates/security/login.html.twig:13`: change `path('app_logout')` to `path('logout')`.
- Test: `loginUser()` with the fixture admin, then GET `/login`, assert 200 and that the logout link is present.

### 1.2 CSRF-protected deletes (finding #4)
Done in PR #10.
- In `EventInvitationController`, `EventChronicleController` and `BlogController`, change the `*_delete_yes` routes to `methods: ['POST']`. Validate a token with `$this->isCsrfTokenValid('delete-'.$entity->getId(), $request->getPayload()->getString('_token'))`, and throw `AccessDeniedException` (or redirect with a flash message) when the token is invalid.
- Replace the "Chcem zmazať" `<a href>` links with small `<form method="post">` elements that carry a hidden `_token` (`csrf_token('delete-' ~ entity.id)`). The links are in:
  - `templates/event_invitation/delete.html.twig`
  - `templates/event_invitation/showEventInvitationByYearBySlug.html.twig` (modal)
  - `templates/event_chronicle/delete.html.twig`
  - `templates/event_chronicle/showChronicleByYearSlug.html.twig` (modal)
  - `templates/blog/delete.html.twig`
  - `templates/blog/showBlogByBlogSectionSlugYearSlug.html.twig` (modal)
- Tests: an anonymous POST redirects (302) to login; an admin GET gets 405; an admin POST without a token is rejected; an admin POST with a valid token deletes and redirects. Update the existing data providers that expect 302 for GET on `/delete/yes`.

### 1.3 `/blog/viacdnove-akcie` crashes on a blog with no start date (finding #5)
Done in PR #9 (both a and b).
- Pick one fix (or both):
  - **a)** In `BlogController::createBlog` and `editInvitation`, make `startDate` required for section 2 (add a `NotBlank` constraint when the field is kept).
  - **b)** In `BlogRepository::getPreparedByYearStartDate()`, fall back to `createdAt` when `startDate` is null: `($blog['startDate'] ?? $blog['createdAt'])->format('Y')`.
- Recommendation: do both. **a)** stops new bad data, and **b)** keeps rows that already exist from crashing the page.
- Test: add a fixture blog in section 2 with a null `startDate`, then GET `/blog/viacdnove-akcie` and assert 200.

### 2.2 Use the correct year and section in blog links (finding #6)
Done in PR #9. Decided: `createdAt` is the canonical year in blog URLs.

### 2.3 Correct latest plan year (finding #2)
Done in PR #9.
- Replace `EventRepository::findMaxStartDate()` and `findMaxStartYear()` with one query:
  ```php
  $max = $this->createQueryBuilder('e')
      ->select('MAX(e.startDate)')
      ->where('e.publish = 1')
      ->getQuery()
      ->getSingleScalarResult();      // null when there are no rows
  return $max === null ? null : (int) substr((string) $max, 0, 4);
  ```
- Remove `findMaxStartDate()` if nothing else uses it (check with `grep -rn findMaxStartDate src tests`).
- Tests: with the fixture events across several years, the home page "Plán na rok" link shows the highest year; with an empty table (or a dedicated test), `/plan` returns 404, not 500.

### 2.4 Unique slugs (finding #10)
Done in PR #13 (`App\Service\SlugGenerator`).
- Add a small service, for example `App\Service\SlugGenerator`, with a method `uniqueSlug(string $title, callable $exists): string` that appends `-2`, `-3`, … until `$exists($slug)` is false. Leave out the current entity's own id so that editing doesn't rename the entity to `-2`.
- Use it in the create and edit actions of all three controllers. The year scope is `startDate` for invitations and chronicles, and section plus `createdAt` for blogs.
- Optional: add a database index on `(slug)` per table. A unique constraint can't include the year column cheaply, so the service is the guard.
- Fixtures: `SlugTrait` can stay, because fixtures have no duplicate titles.
- Test: create two invitations with the same title in the same year; both URLs resolve to different invitations.

### 2.5 Pre-fill routes when creating from a planned event (finding #9)

- Simplify the loop to `foreach ($source->getRoutes() as $route) { $chronicle->addRoute($route); }`.
- Update the domain-model docs (then in CLAUDE.md, now `docs/agents/content.md`) so they state the rule that was chosen.
- Test: create a chronicle for the date of a fixture event that has an invitation with routes; the form shows those routes pre-filled.

## Phase 3: Caching

### 3.1 Expire the home-page cache daily (finding #3)
Done in PR #11.
- Inside the `HomePageController::index` cache callback: `$item->expiresAt(new \DateTimeImmutable('tomorrow'));`
- Optionally do the same for `main-menu-data`. It holds no date-relative data, so this is not required.
- Test: hard to test end to end. Add a unit test for the callback or rely on a manual check. At minimum, make sure no existing test regresses.

### 3.2 Use the test database for the cache (finding #8)
Done in PR #11. Decided: option B, the `content.cache` pool.
- Option A, minimal: build the adapter from the Doctrine connection instead of the env var. Make `SecondLevelCachePDO` a regular service that receives `Doctrine\DBAL\Connection $connection`, then `new DoctrineDbalAdapter($connection, 'app')`. Inject it into `HomePageController`, `Menu\Builder` and the write actions, replacing `SecondLevelCachePDO::getInstance()`.
- Option B, more idiomatic: define a cache pool in `config/packages/cache.yaml` (`app.content_cache` with `adapter: cache.adapter.doctrine_dbal` and `provider: doctrine.dbal.default_connection`). Inject `TagAwareCacheInterface`/`CacheInterface` and call `invalidateTags` or `delete`.
- Either option also removes the static state, so the FrankenPHP worker-mode restriction can be revisited later.
- Update the agent docs (then CLAUDE.md, now `docs/agents/content.md` and `AGENTS.md`): the caching rule (the singleton and the `clearAllCache()` rule move to an injected service) and the Docker worker-mode note.
- Test: running the suite no longer touches the dev database's `cache_items` table. Check manually by clearing the dev cache, running the tests and confirming the table is still empty.
