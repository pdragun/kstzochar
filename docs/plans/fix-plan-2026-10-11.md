# Fix plan for the 2026-10-11 security and test coverage review

Source: the `/code-review` run of 2026-10-11 (security and test coverage, whole project). The numbering below follows that review's summary:

1. no login throttling
2. GPX served by id without a publish check
3. unsanitized `|raw` article HTML, no security headers
4. `{date}` route parameter not validated
5. menu lists years with only unpublished events
6. GET logout without CSRF
7. no test for a member without `ROLE_ADMIN`
8. no test through the real login form
9. no test that unpublished content returns 404
10. GPX test checks only the status code

**Status: done.** Phase 1 in PR #30, phase 2 in PR #31 (2026-10-11), phase 3 in PR #32 and phase 4 in PR #33 (2026-10-14).

All findings were checked against the code before writing this plan.
Each phase ships as its own branch and pull request, and the phases don't depend on each other. Every step adds or updates a functional test in `tests/Controller/`. After each phase run `task check` (phpstan, rector:check, phpunit).

## Phase 1: Login and access control (findings #1, #6, #7, #8)

Done in PR #30.

### 1.1 Throttle login attempts (#1)
- `config/packages/security.yaml`, `main` firewall: add `login_throttling: { max_attempts: 5, interval: '15 minutes' }`. `symfony/rate-limiter` and `symfony/lock` are already installed.
- The limiter state lives in `cache.rate_limiter` (`cache.app`, filesystem). In the test env it survives between runs, so either point it at an array pool under `when@test`, or reset the limiter in the test's `setUp()`.
- Check that the "too many attempts" message has a Slovak translation (`security` domain). If it doesn't, add one to `translations/security.sk.yaml`.
- Test: post a wrong password 5 times, then assert that the 6th attempt, even with the right password, stays on `/login` and shows the throttling message.

### 1.2 Logout with a CSRF token (#6)
- `security.yaml`: `logout: { path: logout, target: home_page, enable_csrf: true }`.
- `templates/security/login.html.twig:13`: replace `path('logout')` with `logout_path()`. It adds the `_csrf_token` query parameter, so the route can stay GET. That is the only logout link (`grep -rn logout templates src/Menu`).
- Tests: a logged-in GET `/logout` without a token doesn't log out; following the link from `/login` does.

### 1.3 Tests through the real login form (#8)
- New `tests/Controller/LoginFormTest.php`:
  - submit the fixture admin's credentials with `$client->submitForm()`, then assert a redirect and that an admin page returns 200;
  - submit a wrong password and assert the error message on `/login`;
  - post with a bad `_csrf_token` and assert that the login fails.
- The fixture passwords are in `src/DataFixtures/UserFixtures.php`.

### 1.4 Members without ROLE_ADMIN are refused (#7)
- Add a data provider with every admin route: the create, edit and delete routes of invitations, chronicles and blogs, plus `/miesta-stretnutia` and its edit, merge and delete. Log in as `jana.novakova@example.com` and assert 403 for each.
- Reuse the existing admin-route data providers where possible, so that a new admin route is covered once it is added there.

## Phase 3: Strict date parameter (finding #4)

Done in PR #32.

- `EventInvitationController.php:145` and `EventChronicleController.php` (the `.../pridat-novu/{date}/add` route): add `requirements: ['date' => '\d{4}-\d{2}-\d{2}']`.
- Replace `new DateTimeImmutable($date)` with `DateTimeImmutable::createFromFormat('!Y-m-d', $date)`, and throw `createNotFoundException()` when it returns `false` or when the formatted result differs from `$date` (this rejects `2026-02-31`).
- Tests (admin): `/pozvanky/2026/pridat-novu/abc/add` → 404, `.../2026-02-31/add` → 404, `.../2026-10-11/add` → 200; the same for chronicles.

## Phase 4: HTML sanitizing and security headers (finding #3)

Done in PR #33. Decided: no iframes in the allowlist (no content uses them), sanitize on save and on render (option a). The `style` and `class` attributes are allowed for CKEditor's formatting, and the input length limit is turned off.

Open follow-up: a full script CSP (4.2).

### 4.1 Sanitize article HTML
- `composer require symfony/html-sanitizer`, then define a sanitizer `app.article_sanitizer` in `config/packages/html_sanitizer.yaml`. Base it on `allow_safe_elements`, and allow what CKEditor produces: tables, images, links with `target`, headings and lists.
- **Decision needed:** does real content embed iframes (maps, YouTube)? Before choosing the allowlist, check production with `SELECT id FROM event_invitation WHERE content LIKE '%<iframe%'` (and the same for chronicles and blogs). If there are any, allow `iframe` only from those hosts (`allow_element('iframe', [...])` together with `allowed_link_hosts`/media hosts).
- Where to sanitize: on save, in the forms. Set the `sanitize_html: true, sanitizer: 'app.article_sanitizer'` option on the content `CKEditorType` fields of the invitation, chronicle and blog forms. Existing rows aren't cleaned by that, so also either:
  - **a)** add a Twig filter (`|sanitize_html('app.article_sanitizer')`) in place of `|raw` in the 6 templates, which cleans on render and costs a little CPU; or
  - **b)** add a one-off console command that re-saves all content through the sanitizer.

  Recommendation: **a)**, because it covers old data without a data migration and the pages are small. Sanitizing on save is then defence in depth.
- Test: save an invitation whose content has `<img src=x onerror=alert(1)>` and `<script>`, then assert that the detail page has neither `onerror` nor `<script>` in the content, and that normal formatting (`<strong>`, `<table>`) is kept.

### 4.2 Security headers
- Add a small `kernel.response` listener (`App\EventListener\SecurityHeadersListener`) that sets:
  - `X-Frame-Options: DENY`
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - `Content-Security-Policy: frame-ancestors 'none'`
- A full script CSP is a separate step. The inline JSON-LD, gtag (consent mode), CKEditor and the Encore bundles need nonces or hashes. Start with `Content-Security-Policy-Report-Only` only if a report endpoint is wanted; otherwise leave it out of this PR.
- Shared hosting runs Apache, so the listener (not the Caddyfile) is the place that works in both environments.
- Test: GET `/` and assert the headers.
