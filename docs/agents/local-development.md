# Local development: details

The rules every task needs are in `AGENTS.md` → Local development. This file has the details for when you work on the stack itself or something about it goes wrong.

- **File ownership.** The dev php image runs as a user `app` with your host user's ids (`USER_UID`/`USER_GID` build args in `compose.override.yaml`; Task passes yours, a bare `docker compose` assumes 1000:1000), and the node service runs as you too. Everything they write into the bind-mounted project (`var/`, `vendor/`, `node_modules/`, `public/build/`, generated code, migrations) stays yours. Don't use `-u root` for project commands. `task fix-perms` is only for files left by a stack that ran as root; after changing your ids, rebuild with `task up`.
- **Logs.** `var/` lives in the project directory, so read `var/log/dev.log` and `var/log/test.log` directly; `task logs -- php` shows FrankenPHP's output, and the web profiler is at `/_profiler`.
- **Startup.** The php container's entrypoint runs `composer install` only when `vendor/` is empty, waits for the database and runs pending migrations, if the project has any. It boots `bin/console` first, which fails on a `vendor/` older than `composer.lock` (a pull that adds a bundle), so `task up` runs `composer install` in a one-off container before it starts the stack whenever `composer.lock` is newer than `vendor/composer/installed.json` (after a pull, checkout or merge). After changing the lock with the stack already running, run `task install` yourself. With `--watch`, FrankenPHP restarts its PHP workers when files change.
- **Configuration.** `.env` is committed and holds defaults only. Real secrets go in `.env.local` (git-ignored) or the secrets vault (`task console -- secrets:set`). Compose takes the host ports from the shell environment (`HTTP_PORT`, `HTTPS_PORT`, `HTTP3_PORT`, `DATABASE_PORT`); `AGENTS.md` lists the project's defaults.
- **Permissions.** `.claude/settings.json` allows only low-risk tasks without a prompt: of `bin/console`, only `about`, `debug:*` and `lint:*`. Everything else (other console commands, `task sh`, `task docker:exec`, Composer, npm, resetting the database) asks first. `task check:permissions` fails if an allow rule in `.claude/settings.json` or `.claude/settings.local.json` (where "don't ask again" adds rules) names a task that doesn't exist, or if those files or the user's Claude Code settings let a risky command run without a prompt: a probe from `taskfiles/check-permissions.sh`, any command of a task whose arguments run code (such as `task npm -- *`) other than a few safe ones, a bare `Bash` rule or the `bypassPermissions` mode. A Claude Code hook runs it after each edit of `Taskfile.yaml`, `Taskfile.local.yml`, `taskfiles/common.yaml`, `taskfiles/check-permissions.sh` or the settings, and another refuses every Bash command while such a risky rule exists (when the check can't run, such as without jq, it warns instead). When you add a task that runs arbitrary commands, changes or deletes data, or never returns, add it to the probes in `taskfiles/check-permissions.sh` in the same change. Write allow rules for a task as `task x` and `task x -- *`, never `task x:*` or `task x *`: Task runs every task named on its command line, so a wildcard before ` -- ` lets any other task run too (`check:permissions` flags it).
