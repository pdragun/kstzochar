# Local development: details

The rules every task needs are in `AGENTS.md` → Local development. This file has the details for when you work on the stack itself or something about it goes wrong.

- **File ownership.** The dev php image runs as a user `app` with your host user's ids (`USER_UID`/`USER_GID` build args in `compose.override.yaml`; Task passes yours, a bare `docker compose` assumes 1000:1000), and the node service runs as you too. Everything they write into the bind-mounted project (`var/`, `vendor/`, `node_modules/`, `public/build/`, generated code, migrations) stays yours. Don't use `-u root` for project commands. `task fix-perms` is only for files left by a stack that ran as root; after changing your ids, rebuild with `task up`.
- **Logs.** `var/` lives in the project directory, so read `var/log/dev.log` and `var/log/test.log` directly; `task logs -- php` shows FrankenPHP's output, and the web profiler is at `/_profiler`.
- **Startup.** The php container's entrypoint runs `composer install` only when `vendor/` is empty, waits for the database and runs pending migrations, if the project has any. It boots `bin/console` first, which fails on a `vendor/` older than `composer.lock` (a pull that adds a bundle), so `task up` runs `composer install` in a one-off container before it starts the stack whenever `composer.lock` is newer than `vendor/composer/installed.json` (after a pull, checkout or merge). After changing the lock with the stack already running, run `task install` yourself. With `--watch`, FrankenPHP restarts its PHP workers when files change.
- **Configuration.** `.env` is committed and holds defaults only. Compose fills `${VAR}` in the compose files from the shell (Task adds `.taskfile.local` where `Taskfile.yaml` loads it with `dotenv:`) and from the project's `.env`, which is Symfony's committed one; that is how it takes the host ports (`HTTP_PORT`, `HTTPS_PORT`, `HTTP3_PORT`, `DATABASE_PORT`). `AGENTS.md` lists the project's defaults.
  - **Load order.** Symfony loads `.env`, `.env.local`, `.env.<APP_ENV>`, then `.env.<APP_ENV>.local`, and a later file wins. The test environment skips `.env.local`.
  - **Secrets** go in a git-ignored file, never in a committed `.env*`: `.env.local`, or `.env.<APP_ENV>.local` when a committed `.env.<APP_ENV>` sets the same variable (it beats `.env.local`), and `.env.test.local` for tests. A committed `.env.dev` or `.env.test` holds only throwaway values, such as the recipe's `APP_SECRET`.
  - **Real environment variables** (every variable a compose service sets under `environment:`, the prod server) beat every file, even when set but empty. That includes the ones compose fills only from a default, such as `SERVER_NAME` and `DATABASE_URL` in `compose.yaml`: setting them in `.env.local` has no effect inside the container. Change them in the compose files, or the `${VAR}` they are built from where compose takes it (above); a secret or a value for your machine only goes in `.taskfile.local`, never in a committed file (where `Taskfile.yaml` doesn't load it, add `dotenv: ['.taskfile.local']` there and the file to `.gitignore` first). The database applies its name, user and password only when its volume is created.
  - **The vault** (`secrets:set`) supplies a variable only when no `.env*` file and no real environment variable gives it a non-empty value. The dev vault's decryption key is committed, so no real secret goes there; a prod vault's private key stays out of git and out of the image.
  - **Traps.** `APP_ENV` comes from the real environment, `.env` or `.env.local`, never from a later file; where compose sets it (`${APP_ENV:-dev}`), the container gets it from the shell or `.env` when it starts, and `--env` overrides it for one console command. A git-ignored `.env.local.php` (written by `composer dump-env`) replaces every `.env*` file unless the real environment sets a different `APP_ENV`: when edits to `.env*` have no effect, look for a stale one.
- **Permissions.** `.claude/settings.json` allows only low-risk tasks without a prompt: of `bin/console`, only `about`, `debug:*` and `lint:*`. Everything else (other console commands, `task sh`, `task docker:exec`, Composer, npm, resetting the database) asks first. `task check:permissions` fails if an allow rule in `.claude/settings.json` or `.claude/settings.local.json` (where "don't ask again" adds rules) names a task that doesn't exist, or if those files or the user's Claude Code settings let a risky command run without a prompt: a probe from `taskfiles/check-permissions.sh`, any command of a task whose arguments run code (such as `task npm -- *`) other than a few safe ones, a bare `Bash` rule or the `bypassPermissions` mode. A Claude Code hook runs it after each edit of `Taskfile.yaml`, `Taskfile.local.yml`, `taskfiles/common.yaml`, `taskfiles/check-permissions.sh`, `taskfiles/permission-probes` or the settings, and another refuses every Bash command while such a risky rule exists (when the check can't run, such as without jq, it warns instead). When you add a task that runs arbitrary commands, changes or deletes data, or never returns, add it to the probes in the same change: a general one in `taskfiles/check-permissions.sh`, this project's own in `taskfiles/permission-probes` (one command per line). An allow, ask or deny rule for this project's own task goes in `.claude/settings.json` too, and stays there when the setup files are updated. Write allow rules for a task as `task x` and `task x -- *`, never `task x:*` or `task x *`: Task runs every task named on its command line, so a wildcard before ` -- ` lets any other task run too (`check:permissions` flags it).
